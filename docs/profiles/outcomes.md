# Що показали профілі й перевірка після правок

План до змін зафіксований окремим комітом 5492b5b. Тут — висновки.

1. **load/validate.** Перевірку структури не вимкнено. Посилання на mapping
   довжин береться один раз, а не через новий MappingProxyType для кожної позиції.
   HTTP-сервіс, як і раніше, завантажує індекс один раз через lifespan.
2. **Снипети / нормалізація.** Спочатку Unicode-сканування перенесено в regex.
   Одного цього виявилося недостатньо (близько 1.15× на повному пошуку).
   Кеш 8192 словоформ прибрав повторні tokenize для однакових слів і дав 3.27×
   на проміжному прогрітому замірі. Фінальні цифри — в speed.json.
3. **tokenize/build_state.** Нормалізація Unicode та regex вже мають native-частину.
   Формат тексту й правила не спрощувалися заради швидкості. Побудова лишається
   в CPU-конвеєрі лабораторної 5. Прискорення індексації не приписується NumPy-скореру.

## Помилка під навантаженням: занадто часті передачі GIL

На одному запиті код виглядав швидким, але 20 потоків поводилися погано.
`regex` за замовчуванням може відпускати GIL під час роботи зі строкою.
Для багатьох коротких збігів це створювало часті переключення між потоками.
Контрольований дослід на тому самому індексі, 20 викликів search через
ThreadPoolExecutor(20):

| regex.finditer | Wall time, с |
|---|---:|
| типова поведінка | 5.451 |
| concurrent=False | 0.499 |

Сирі результати: [regex-contention.json](../../benchmarks/lab08/regex-contention.json).
Це один окремий діагностичний запуск, не медіана основної таблиці скорерів.
Вибрано concurrent=False лише для короткого сканування снипетів, а не для всіх
операцій застосунку. NumPy й ONNX продовжують виконувати власний native-код.

До цієї правки прогрітий публічний тест c=20 мав p95 41.39 с, усі 20 відповідей
були HTTP 200. Файл збережено як deployed-before-gil-fix.json. Фінальний повтор
з тією самою методикою зберігається в deployed-oha.json. Негативні заміри не видалено.

Також тест показав, що RRF міг залишати порожній снипет від lexical-списку:
тепер він бере доступний фрагмент із semantic-списку. На це є регресійний тест.

## Межі висновків

cProfile разом із CLI tracemalloc суттєво сповільнює виконання; його абсолютні
секунди не порівнюються з HTTP або непрофільованим scoring-only. Scalene на
Windows дає sampled розподіл Python/native/system, а не точну атрибуцію всіх
машинних інструкцій. P@5 і швидкість виміряні окремо: швидка функція може дати
гіршу релевантність, і навпаки.
